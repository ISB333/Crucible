## Overview

Crucible is a Python-based, verifier-grounded multi-agent search engine built to systematically evaluate and iteratively refine solutions for computational tasks. The system shifts the standard of correctness away from probabilistic model confidence toward deterministic external verification. It operates by defining tasks that contain both immutable regions and explicit editable holes. 

To solve these tasks, Crucible deploys an optimization loop utilizing parallel, sandboxed Large Language Model (LLM) workers. These agents propose edits to the defined holes, verify the resulting artifacts in isolated sandbox environments, and iteratively incorporate feedback from the deterministic verifiers to converge on a correct solution.

## Architecture

Crucible follows an orchestrator-worker architecture that strictly separates execution environments, LLM generation providers, and custom task verifiers. This isolation guarantees that sandboxed workers can safely execute generated code or scripts while the orchestrator manages the state machine and coordinates the overarching search and optimization loop.

### Core Module Breakdown

The system is highly modular, driven by a central CLI that delegates core logic to an internal SDK and orchestration tier.

- **CLI Interface (`crucible/cli.py`)**: The main user entry point for initiating task evaluations. The CLI acts as the dependency root, directly wiring together the SDK, task definitions, verifiers, budgets, and storage mechanisms.
- **Orchestration (`crucible/orchestrator.py`)**: The engine of the multi-agent search. It coordinates the parallel execution loop, dispatches work to sandboxed LLM workers, incorporates verification feedback, and tracks iteration state.
- **Task Management (`crucible/task.py`)**: Defines the boundaries of the problems being solved, specifically tracking the immutable regions versus the explicitly editable holes that agents are permitted to modify.
- **Artifacts (`crucible/artifact.py`)**: Represents the discrete files, code blocks, or textual outputs generated by the LLMs before and after being injected into the editable holes.
- **Verification (`crucible/verify.py` & `verifiers/`)**: Contains the deterministic external verifiers that evaluate the correctness of the LLM-generated artifacts. These modules provide the grounding feedback required by the orchestrator.
- **LLM Integration (`crucible/llm.py`)**: The abstraction layer for communicating with various external LLM providers, ensuring the orchestrator remains agnostic to the underlying model being queried.
- **Advisors (`crucible/advisor.py`)**: Supplementary modules that provide heuristic guidance or intermediate feedback to the agents during the optimization loop.
- **Budgets (`crucible/budgets.py`)**: Resource tracking modules that enforce limits on the optimization loop (e.g., maximum iterations, token limits, or parallel worker constraints) to prevent runaway execution.
- **Storage (`crucible/store.py`)**: Handles the persistence of task states, historical iterations, and agent trajectories throughout the evaluation lifecycle.

### Component Dependencies

Execution flows top-down from the CLI into the core processing modules:
1. The `cli` module directly orchestrates the `sdk`, `verifiers`, `task`, `budgets`, `store`, and `verify` components.
2. The `sdk` acts as a facade and functional core, managing internal dependencies to `orchestrator`, `advisor`, `artifact`, `budgets`, and `llm`. 

## API Surface

Crucible operates strictly as a local execution engine and CLI tool. It does not expose any public HTTP routes, REST/GraphQL endpoints, or WebSocket events. All external communication is outbound, directed toward third-party LLM provider APIs.

## Data Models

The system does not utilize a relational database, ORM models, or database migration scripts. Application state, task definitions, and iterative refinement trajectories are handled in-memory and persisted via the local file system or custom storage abstractions defined within the `store` module.

## Configuration

Crucible integrates with multiple external LLM providers and is configured via environment variables. This allows the orchestrator to dynamically route generation tasks to different models or local endpoints.

- `ANTHROPIC_API_KEY`: Authenticates connections to Anthropic's Claude models.
- `GOOGLE_API_KEY` (or `GEMINI_API_KEY`): Authenticates connections to Google Gemini models.
- `OPENAI_API_KEY`: Sets the API key for OpenAI models or acts as the authorization token for compatible local/remote models.
- `OPENAI_BASE_URL`: Defines a custom base URL for OpenAI-compatible endpoints, enabling seamless integration with alternative remote APIs or local LLM runtimes (e.g., vLLM, Ollama).
